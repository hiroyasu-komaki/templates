# ガバナンス文書標準テンプレート（govdoc-template）

会議体・承認プロセスを伴う**ガバナンス運営の文書一式**の標準構成。

---

## フォルダ構成

```
govdocs/
├─ README.md                           このファイル
├─ rules/                              【規範】何を守るか
│  ├─ 01-policy.docx                   方針
│  ├─ 02-charter.docx                  会議体規程
│  ├─ 03-standard.docx                 運用基準
│  ├─ 04-delegation-of-authority.xlsx  決裁権限表
│  └─ 05-guideline.md                  ガイドライン
├─ process/                            【プロセス】どう動くか
│  ├─ 01-process-definition.pptx       業務フロー定義
│  ├─ 02-sop.docx                      標準作業手順書
│  ├─ 03-runbook.md                    事務局Runbook
│  ├─ 04-playbook.md                   Playbook
│  ├─ 05-work-instruction.pptx         作業指示書
│  └─ 06-checklist.xlsx                チェックリスト
└─ reference/                          【参照】何を見ればよいか
   ├─ 01-handbook.pptx                 起案者ガイド
   ├─ 02-faq.md                        FAQ
   ├─ 03-glossary.md                   用語集
   ├─ 04-decision-log.xlsx             決定記録
   ├─ 05-form-template.docx            様式のひな型
   └─ 06-calendar.xlsx                 年間カレンダー
```

## 1. 目的

新しいガバナンスの仕組み（例: IT投資ガバナンス、ベンダーマネジメント、データガバナンス）を立ち上げるときに、「何を守るか」「どう動くか」「何を見ればよいか」を、抜けと重複なく文書として揃えられるようにする。

このテンプレートで解決したいこと:

- **文書間の食い違いを防ぐ。** 基準を1か所にだけ書き、他の文書はそこを参照する構成にする。
- **ルールを変えずに運用を改善できるようにする。** 承認の重い文書と軽い文書を分け、運用の見直しで規程の改訂が要らないようにする。
- **立ち上げに必要な文書を絞る。** 最初から全文書を揃えず、初期セットで運用を始め、必要になった文書を後から足す。

## 2. 文書の定義

### 2-1. 文書体系（3層）

ガバナンス文書は、**変わりにくさ**と**承認の重さ**で3層に分ける。

```
rules/      規範    … 何を守るか       変わりにくい／承認が重い（経営層・会議体）
   ↓ 参照
process/    プロセス … どう動くか       運用で見直す／承認が軽い（事務局責任者）
   ↓ 参照
reference/  参照    … 何を見ればよいか  随時更新／承認不要（事務局）
```

- **下位の文書は上位の文書を参照する。上位の文書の内容を書き写さない。** Runbookに基準額を書き込むと、基準の改訂のたびにRunbookも改訂が必要になる。基準額は運用基準に書き、Runbookからは「運用基準 第○条」と参照する。
- **文書間で食い違ったら、上位の文書を正とする。** rules > process > reference の順。
- **上位・下位の関係と、書く順番は別。** 書き始めるのは業務フロー定義から（§3-1）。

### 2-2. 全17文書の定義

○ の列で、運用開始までに整備する文書（**初期**）と、必要になったときに追加する文書（**後続**）を示す。

**rules/（規範）**

| # | 文書 | 定義（何を書くか） | 初期 | 後続 |
|---|---|---|:---:|:---:|
| 01 | 方針（Policy） | 仕組みの目的・原則・適用範囲・役割の大枠 | | ○ |
| 02 | 会議体規程（Charter / ToR） | 会議体ごとの目的・構成員・権限・付議基準・運営方法 | ○ | |
| 03 | 運用基準（Standard） | 判定基準・閾値・判断区分・提出要件 | | ○ |
| 04 | 決裁権限表（DoA） | 誰が何を、どの条件で決裁できるか | ○ | |
| 05 | ガイドライン（Guideline） | 推奨事項（守らなくても違反ではない） | | ○ |

**process/（プロセス）**

| # | 文書 | 定義（何を書くか） | 初期 | 後続 |
|---|---|---|:---:|:---:|
| 01 | 業務フロー定義（Process Definition） | 全体の流れ、関係者、受け渡し、RACI | ○ | |
| 02 | 標準作業手順書（SOP） | 品質・監査上の要求がある業務の正式手順 | | ○ |
| 03 | Runbook | 事務局の定型作業の手順（入力・作業・出力・期限・担当） | ○ | |
| 04 | Playbook | 例外や判断が必要な状況で、どう判断し誰が決めるか | | ○ |
| 05 | 作業指示書（Work Instruction） | システム操作など1作業の細かい手順 | | ○ |
| 06 | チェックリスト（Checklist） | 確認項目と、案件ごとの確認結果 | | ○ |

**reference/（参照）**

| # | 文書 | 定義（何を書くか） | 初期 | 後続 |
|---|---|---|:---:|:---:|
| 01 | 起案者ガイド（Handbook） | 申請者向けの流れ・書き方・締切 | ○ | |
| 02 | FAQ | よくある質問と回答 | | ○ |
| 03 | 用語集（Glossary） | 用語の定義と使い分け、旧制度の用語との対応 | ○ | |
| 04 | 決定記録（Decision Log） | 決定事項・保留課題（TBD）・確認依頼 | ○ | |
| 05 | 様式のひな型（Template） | 起案書・議事録などの様式を作るときの共通ひな型 | | ○ |
| 06 | 年間カレンダー（Calendar） | 会議日程・締切（外部の基準日からの逆算） | | ○ |

### 2-3. 後続の文書の代替

初期セットに入らない文書の役割は、運用開始時点では初期セットの文書で代替する。

| 後続の文書 | 運用開始時点での代替 |
|---|---|
| 方針 | 経営層の決定事項（議事録・通達）を会議体規程の上位文書として参照する |
| 運用基準 | 会議体規程の中に判定基準を書く |
| Playbook | Runbookの「例外対応」の章に書く |
| チェックリスト | Runbookの事前チェックの手順に確認項目を列挙する |
| FAQ・ガイドライン | 起案者ガイドに要点を書く |
| 年間カレンダー | 起案者ガイドのスケジュールのスライドに書く |

### 2-4. 参照関係（どちらが上位か）

```
01-policy ──→ 02-charter ──→ 03-standard ──→ 04-delegation-of-authority
                  │                │                    │
                  └────────────────┴────────────────────┴──→ process/01-process-definition
                                                                      │
                          ┌───────────────┬──────────────────┬───────┴────────┐
                          ↓               ↓                  ↓                ↓
                     02-sop         03-runbook ←→ 04-playbook      06-checklist
                                          │
                                          └──→ 05-work-instruction

reference/ は全文書から参照される（用語集・様式・カレンダー・決定記録）
```

## 3. 初期セットアップ

### 3-1. 書く順番

**業務フロー定義から書く。** 会議体・決裁権・基準は、業務の流れ（誰が・いつ・何を決め、何を誰に渡すか）を条文の形に固めたもの。流れを描く前に規程を書くと、会議体の権限の重なりや、受け渡しの抜けに気づけない。

```
① 業務フロー定義（草案）   流れ・関係者・RACI を描く。未確定の箇所は（TBD）のまま
        ↓
② 会議体規程・決裁権限表    フローの「決める箱」と RACI の A を、権限として条文・表にする
        ↓
③ 業務フロー定義（確定）   ②で決まった権限をフローに反映する
        ↓
④ Runbook                 フローの箱ごとに事務局の手順を書く
   起案者ガイド              申請者側から見たフローを書く

用語集・決定記録は ① から並行して書き足していく
```

経営層の方針が先に示されている場合（例: 仕組みの導入そのものが経営層で決定済み）は、その決定事項を①の前提として扱う。

### 3-2. 初期セットの準備

> 情報が揃わないまま書くと、推測で埋めた箇所が「決まったこと」として読まれる。集まらなかった情報は書かずに `（TBD: 〜）` として残し、決定記録の保留課題に登録する。
>
> 情報の多くは、既存の規程・過去の会議記録・関係者の頭の中にある。**新しく決めることと、既にあるものを書き起こすことを分けて進める。**

| 順 | 文書 | 集めておく情報 | 集めるための活動 |
|---|---|---|---|
| ① | [業務フロー定義](./process/01-process-definition.pptx) | ・仕組みの開始点と終了点（何が起きたら始まり、何で終わるか）<br>・関係者（部署・会議体・システム）<br>・現行の流れと、変える点<br>・関係者間で受け渡すもの（書類・情報・決定）<br>・外部の業務（予算編成・調達・契約）との接点 | ・現行の流れの可視化（旧制度の規程・議事録・様式から描き起こす）<br>・過去の案件1〜2件を最初から最後まで追跡する（ウォークスルー）<br>・関係部署を集めたフローのレビュー（ワークショップ形式）<br>・RACIの「A」を関係者と確認する |
| ② | [会議体規程](./rules/02-charter.docx) | ・経営層が決めた仕組みの目的と範囲<br>・会議体ごとの目的、構成員（役職）、議長<br>・会議体ごとの決定事項と、上位・下位の関係<br>・開催頻度、定足数、決議方法<br>・旧制度の会議体と、その規程・内規（置き換えるもの） | ・経営層・所管役員へのヒアリング（目的と権限の確認）<br>・既存の規程・内規・職務権限規程の棚卸し<br>・旧会議体の議事録・付議実績の確認（件数・所要時間）<br>・会議体の議長候補への事前説明と合意 |
| ② | [決裁権限表](./rules/04-delegation-of-authority.xlsx) | ・判定軸とその区分（例: 予算区分、組織区分、予算の所在、外部性）<br>・金額の閾値<br>・決裁者と、合議・報告を受ける者<br>・委任を認める条件と報告義務<br>・全社の職務権限規程との関係 | ・全社の職務権限規程・稟議規程の確認（矛盾しないか）<br>・財務部門との協議（予算区分・金額の閾値）<br>・過去の案件を判定軸に当てはめる試行（抜け・重なりの確認）<br>・事業部門・IT部門の責任者との合意形成 |
| ④ | [Runbook](./process/03-runbook.md) | ・業務フロー定義の箱ごとの作業内容<br>・各作業の担当、期限、使う様式・システム<br>・予算編成など外部の締切<br>・過去に起きた例外とその対応 | ・旧制度の事務局担当者へのヒアリング（実際の作業手順）<br>・業務フロー定義のウォークスルーで見つかった作業の細分化<br>・案件管理システムの画面・ステータスの確認 |
| ④ | [起案者ガイド](./reference/01-handbook.pptx) | ・申請の対象と対象外<br>・年間スケジュールと締切<br>・起案書の様式と記入項目<br>・申請者が迷う点、よく間違える点<br>・問い合わせ先 | ・過去の問い合わせ・差し戻し理由の集計<br>・申請経験者（事業部門・IT部門）へのヒアリング<br>・起案書の様式の試行記入（申請者数名に書いてもらう）<br>・ガイドの草案を申請者に読んでもらうレビュー |
| 並行 | [用語集](./reference/03-glossary.md) | ・規程・基準で使う用語と、その定義<br>・関係者によって意味がずれている用語<br>・旧制度の用語と新制度の用語の対応<br>・略語 | ・既存の規程・資料からの用語の抽出<br>・ヒアリング中に「人によって意味が違う」と気づいた語の記録<br>・関係部署（財務・法務・事業部門）との定義のすり合わせ |
| 並行 | [決定記録](./reference/04-decision-log.xlsx) | ・準備中に決まったこと（誰が・いつ・なぜ）<br>・未確定事項と、その確定期限・担当<br>・関係部署への確認依頼 | ・ヒアリング・ワークショップの結論をその場で登録する<br>・準備の定例ミーティングで保留課題の件数と期限を確認する |

### 3-3. 進め方の目安

1. **既存資料の棚卸し**（規程・内規・議事録・様式・問い合わせ記録）を最初に行う。ほとんどの活動の入力になる。
2. **業務フローを関係者と一緒に描く。** ここで関係者・受け渡し・決める箱が揃えば、他の文書の「集める情報」の多くが埋まる。
3. **ヒアリングは文書ごとではなく相手ごとにまとめる。** 同じ相手に何度も聞かないよう、上の表の「集める情報」を相手別に並べ替えてから臨む。
4. **決裁権限表は過去の案件で試す。** 表だけを見て合意すると、運用を始めてから当てはまらない案件が見つかる。
5. 集めながら、用語集に語を足していく（用語集は最後にまとめて書かない）。

## 4. 使い方

### 4-1. コピーして始める手順

1. このフォルダをテーマのフォルダへ `govdocs/` としてコピーする。
   ```bash
   cp -R govdoc-template <テーマのフォルダ>/govdocs
   ```
2. §4-2 の変数一覧を埋め、各ファイルの `{{変数名}}` を置換する。
3. §2-2 で「初期」に ○ がある文書を、§3-1 の順番で書く。
4. 各ファイルの `📝 記入ガイド` を読んで本文を書き、**書き終えたら記入ガイドは削除する。**（残っているファイル＝未完成、と判別できるようにするため）
5. 後続の文書は、まだ使わなくても削除しない。使わないと判断した文書は、冒頭に `⛔ 本テーマでは対象外。理由: ... / 見直す条件: ...` と明記して残す。

### 4-2. 変数一覧

**テンプレートをコピーしたら最初にここを埋め、一括置換する。**

| 変数 | 意味 | 記入例 | 本テーマの値 |
|---|---|---|---|
| `{{ORG_NAME}}` | 組織名 | 株式会社○○ | |
| `{{GOV_DOMAIN}}` | ガバナンスの対象領域 | IT投資ガバナンス | |
| `{{DOC_PREFIX}}` | 文書番号の接頭辞 | ITG | |
| `{{OWNER_DEPT}}` | 文書の所管部署 | IT部門 IT企画グループ | |
| `{{SECRETARIAT}}` | 事務局 | IT投資事務局 | |
| `{{SECRETARIAT_HEAD}}` | 事務局責任者 | IT企画グループ長 | |
| `{{POLICY_APPROVER}}` | 方針・会議体規程の承認者 | 経営会議 | |
| `{{STANDARD_APPROVER}}` | 運用基準・決裁権限表の承認者 | Tier2 | |
| `{{MEETING_NAMES}}` | 会議体の名称 | Tier1 / Tier2 / Tier3 | |
| `{{APPLICANT}}` | 申請者（起案者）の呼称 | 起案者 | |
| `{{SUBJECT_UNIT}}` | 審議の単位 | IT投資案件 | |
| `{{FISCAL_YEAR}}` | 対象年度 | 2027年度 | |
| `{{EFFECTIVE_DATE}}` | 施行日 | 2027-04-01 | |
| `{{REVIEW_CYCLE}}` | 定期見直しの周期 | 年1回（予算編成後） | |
| `{{SYSTEM_NAME}}` | 案件管理に使うシステム | 案件管理システム（CMS） | |

**置換の方法**

```bash
# Markdown（macOS）
grep -rl '{{GOV_DOMAIN}}' . --include='*.md' | xargs sed -i '' 's/{{GOV_DOMAIN}}/IT投資ガバナンス/g'

# 置換漏れの確認（Markdown）
grep -rno '{{[A-Z_]\{2,\}}}' . --include='*.md' | sort -u
```

- Word・Excel・PowerPoint は、各アプリの「置換」機能で一括置換する（Excelは「ブック全体」を対象にする）。置換後に `{{` を検索して漏れを確認する。
- `{{日本語の説明}}` 形式のプレースホルダは一括置換の対象外。その場で文章に置き換える。

### 4-3. 記法の約束

| 記法 | 意味 |
|---|---|
| `{{GOV_DOMAIN}}` | 置換必須のプレースホルダ（§4-2 で定義） |
| `{{日本語の説明}}` | その場で文章に置き換える自由記述 |
| `📝 記入ガイド:` | 何を書くかの指示。書いたら削除する |
| `⛔` | 本テーマでは対象外である旨の明示 |
| `（TBD: 〜）` | 未確定事項。確定期限と担当を併記し、[決定記録](./reference/04-decision-log.xlsx) の保留課題に登録する |
| `[任意]` | テーマの性質により省略可能な章・シート |
| `第○条` | 規範文書（rules/）内の条文番号。process/ と reference/ から参照するときに使う |
| Excelの黄色のセル | 入力するセル |
| Excelの灰色斜体の行 | 記入例。書き換えるか削除する |

### 4-4. 文書管理ルール

- **文書番号**: `{{DOC_PREFIX}}-<層>-<連番>`。層は R（rules）/ P（process）/ F（reference）。例: `ITG-R-02`（会議体規程）。
- **版**: 承認を伴う改訂は整数（1.0 → 2.0）、誤字修正など承認不要の改訂は小数（1.0 → 1.1）。
- **文書管理情報**: Word・Excel・PowerPointは冒頭に、Markdownはファイル先頭に、文書番号・版・所管・承認者・最終改訂日・上位文書を置く。
- **改訂履歴**: 各文書の末尾（Excelは「改訂履歴」シート）に残す。
- **定期見直し**: `{{REVIEW_CYCLE}}` ごとに全文書を見直し、見直した結果（変更なしを含む）を改訂履歴に記録する。後続の文書を追加する必要がないかも、このときに確認する。
