# 拡張性への配慮

- **最終更新**: YYYY-MM-DD

> 📝 記入ガイド: **「今回の実装が、将来の追加実装を阻害しないこと」を保証するための設計基準。** 新機能を足すとき・既存を変えるときに、実装者とレビュアーがここに沿っているか確認する。
>
> 段階開発でない場合も、**仕様改訂・機能追加が想定されるなら必要**。「拡張の予定が一切ない」プロジェクトはほぼ存在しない。
>
> 注意: ここは「将来のために作り込む」ためのものではない。**過剰な抽象化は今回のコストを膨らませ、しかも将来の要求に当たらない。** 「今は作らないが、後で足すときに手戻りしない形」を選ぶ、という基準に留める。

## 1. 基本方針

> 📝 記入ガイド: 今回の実装の位置づけを1〜3行で。「まず作って終わり」なのか「土台」なのかを言い切る。

---

## 2. 想定される拡張と、そのための受け口

> 📝 記入ガイド: **「何を拡張するか」が具体的に見えているものだけを書く。** 「いつか必要になるかもしれない」は書かない（YAGNI）。
>
> [プラン比較](../00-overview/02-plan-comparison.md) や [機能スコープ](../01-requirements/03-functional-scope.md) で「今回は除外」とした機能が、そのままここの入力になる。

| 想定する拡張 | 今回やること（受け口の確保） | 拡張時にやること | 受け口が無いと何が起きるか |
|---|---|---|---|
| | | | |

## 3. 先取りして確保するもの

> 📝 記入ガイド: 今回は使わないが、後付けのコストを避けるため先に用意する要素。**必ず「なぜ先取りするか」を書く。** 理由が無いと、レビューで「使われていない」として削除される。

| 対象 | 今回の状態 | 先取りする理由 | 拡張時の使い方 |
|---|---|---|---|
| {{例: DBの列}} | 定義のみ・未使用 | 後付けマイグレーションの手戻り回避 | |
| {{例: 状態の定義}} | 値は定義済み・遷移は未実装 | | |
| {{例: サービス層の分離}} | | 差し込み口の確保 | |

---

## 4. 実装・変更時のチェックリスト

> 📝 記入ガイド: **レビュー時に実際に使えるチェックリストにする。** 抽象的な項目（「拡張性を意識したか」）は無意味。具体的な判定基準を書く。

- [ ] {{仕様項目の追加}}は、{{テーブル変更ではなく定義追加}}で吸収できるか？
- [ ] {{検索・集計が必要な値}}の持ち方は適切か？
- [ ] 将来使う{{列・定義}}は先に確保したか？
- [ ] ビジネスロジックを{{controller/コンポーネント}}に直書きしていないか？
- [ ] 認可が必要な操作は、後から権限判定を差し込める構造か？
- [ ] 文言はハードコードでも、後で辞書化しやすい単位にまとまっているか？
- [ ] {{}}
