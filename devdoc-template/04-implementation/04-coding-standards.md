## 4. コメント

> 📝 記入ガイド: 「コメントを書け」ではなく「**何をコメントすべきか**」を書く。自明なコメントは害。

| 書くべき | 書かなくてよい |
|---|---|
| なぜその実装にしたか（意図） | 何をしているか（コードを読めば分かること） |
| 直感に反する処理の理由 | |
| 一時的な回避策とその解消条件（`TODO:` `FIXME:`） | |
| 業務ルールの根拠（ドキュメントへのリンク） | |

## 9. レビュー観点

> 📝 記入ガイド: **レビュアーが毎回見るチェックリスト。** [実装方針](./01-implementation-policy.md) と [拡張性への配慮](../02-architecture/04-extensibility.md) のルールをここに集約する。
>
> 「読みやすいか」のような主観的項目は入れない。**判定できる項目だけ**にする。

**設計への準拠**

- [ ] [実装方針](./01-implementation-policy.md) §2 のルールに従っているか
- [ ] [拡張性への配慮](../02-architecture/04-extensibility.md) §4 のチェックリストを満たすか
- [ ] レイヤーの責務（[リポジトリ構成](./02-repo-structure.md) §5）を越えていないか

**正しさ**

- [ ] 検証はサーバ側で担保されているか（フロントだけになっていないか）
- [ ] 認可のチェック（所有者・ロール）が入っているか
- [ ] エラー時・空データ時・権限なし時の挙動が実装されているか
- [ ] トランザクション境界は適切か

**保守性**

- [ ] スキーマ・型の単一ソースが守られているか（二重定義していないか）
- [ ] 期限の無い TODO を残していないか
- [ ] 簡易実装は [バックログ](../06-roadmap/02-backlog.md) に登録したか

**ドキュメント**

- [ ] 設計と実装が食い違った場合、設計側を更新したか
- [ ] 設計判断を変えた場合、[ADR](../02-architecture/05-adr/) を追加したか
