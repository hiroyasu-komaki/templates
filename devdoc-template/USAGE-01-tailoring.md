# 使い方①: 案件に応じた取捨選択と記載粒度

**このテンプレートのフルセットが常に必要なわけではない。** 案件の規模・重要性・寿命に応じて、書く章と書き込む深さを選ぶ。

---

## 1. 基本の考え方

ドキュメントの本当のコストは「書く時間」ではなく、**古くなったドキュメントが人を誤誘導するコスト**である。更新されない詳細な設計書は、無いより悪い。

したがって判断基準は「書けるか」ではなく **「更新し続けられるか」**。

| 書くべき | 書かないほうがよい |
|---|---|
| 変更コストが高いもの（データモデル・API契約・権限） | 変更が容易で、コードを見れば分かるもの |
| 決定の理由（コードに残らない） | 決定の結果だけ（コードに残る） |
| 合意の記録（スコープ・前提・除外） | 一度も参照されない網羅的な一覧 |
| 人が入れ替わっても必要な情報 | 今このチームだけが必要な一時情報 |

**書かない判断も記録する。** 章を削除するのではなく、冒頭に `> ⛔ 本プロジェクトでは対象外。理由: ...` を残す。「検討した上で不要と判断した」と「書き忘れた」を区別できることに価値がある。

---

## 2. 案件プロファイルの判定

各軸を評価し、合計点でプロファイルを決める。**迷ったら上のプロファイルを選ぶ**（後から削るのは容易、後から足すのは困難）。

| 軸 | 0点 | 1点 | 2点 |
|---|---|---|---|
| **規模** | 〜3人月 | 3〜20人月 | 20人月〜 |
| **関与人数** | 1〜2名 | 3〜7名 | 8名〜 |
| **想定寿命** | 使い捨て・1年未満 | 1〜3年 | 3年以上 |
| **変更コスト** | 作り直しが容易 | 部分的に高い | 基幹・作り直し不可 |
| **引継ぎ** | 作った本人が使い続ける | チーム内で引き継ぐ | 別組織・別ベンダーへ引き継ぐ |
| **規制・監査** | なし | 社内基準のみ | 法規制・外部監査あり |
| **契約形態** | 社内・見積不要 | 社内・予算管理あり | 受託・契約に基づく |
| **段階開発** | 単発 | 改修の可能性あり | 段階拡張が前提 |

| 合計 | プロファイル | 想定 |
|---|---|---|
| 0〜4点 | **S: 軽量** | PoC、社内ツール、小規模改修 |
| 5〜10点 | **M: 標準** | 業務システム、数年運用、チーム開発 |
| 11点〜 | **L: 重厚** | 基幹・調達・規制対象、長期運用、引継ぎ前提 |

## 3. 記載粒度の3段階

同じファイルでも、書き込む深さを変えられる。

| 粒度 | 内容 | 目安時間 |
|---|---|---|
| **G1 要点** | 見出しを残し、箇条書きで3〜10行。表は主要な行だけ | 15〜30分 |
| **G2 標準** | 主要な表を埋める。「理由」欄は重要なものだけ | 1〜3時間 |
| **G3 詳細** | 全ての表を埋め、却下案・根拠・見直し条件まで書く | 半日〜 |

**粒度を上げる判断**: その表が埋まっていないことで、誰かが判断に迷う／同じ議論が繰り返される／レビューで毎回同じ指摘が出る。

## 5. 規模を問わず必ず書く4つ

上表で太字にしたもの。**S プロファイルでも、この4つだけは省略しない。**

| ファイル | 省略した場合に起きること |
|---|---|
| [機能スコープ](./01-requirements/03-functional-scope.md) | 「やる/やらない」の合意が口約束になり、認識のずれが最後に発覚する |
| [データモデル](./02-architecture/02-data-model.md) | 最も変更コストが高い箇所を、設計せずに作ることになる |
| [開発環境](./04-implementation/03-dev-environment.md) | 新規参加者の立ち上がりに毎回数日かかる。作った本人しか動かせない |
| [バックログ](./06-roadmap/02-backlog.md) | 「後で直す」が全て消える。簡易実装がそのまま本番に出る |

Sプロファイルなら、この4つを G2 で書いて **半日程度**。それでも、書かなかった場合の損失を十分に上回る。

## 6. 章を省略するときの書き方

ファイルを削除するのではなく、内容を消して理由を残す。

```markdown
# 非機能検証

> ⛔ 本プロジェクトでは実施しない。
> 理由: 社内利用・同時利用5名以下・非機能要件に定量目標を置いていないため
>       （→ [非機能要件](../01-requirements/04-non-functional.md)）。
> 見直す条件: 利用部門が拡大し同時利用が20名を超えた場合、または外部公開する場合。
```

**「見直す条件」を書く。** これが無いと、状況が変わっても誰も気づかない。

ファイルごと削除してよいのは、そのプロジェクトで**構造的にありえない**場合だけ（例: ワークフローを持たないシステムの状態遷移設計）。その場合は README のファイル一覧からも削除する。

## 7. 途中でプロファイルが変わったとき

プロジェクトは往々にして「小さく始めて大きくなる」。以下の兆候が出たら、プロファイルを上げて不足章を追加する。

| 兆候 | 追加すべき章 |
|---|---|
| 参加者が増えた／入れ替わった | 04-implementation 全体、00-overview/04-glossary |
| 同じ議論が繰り返される | 02-architecture/05-adr |
| 「これって仕様？バグ？」が頻発する | 01-requirements/03-functional-scope、05-test/02-acceptance-criteria |
| 想定より長く使われることになった | 02-architecture/04-extensibility、08-operations 全体 |
| 別チーム・別組織へ引き継ぐことになった | 08-operations/02-operations-handover、00-overview/03-source-materials |
| 規制・監査の対象になった | 01-requirements/04-non-functional、05-test/03-nfr-verification |
| 段階拡張の話が出てきた | 00-overview/02-plan-comparison、06-roadmap/03-future-plans |

**このとき、既存の章の粒度も上げる必要があるか確認する。** 人が増えれば、G1で足りていた記述がG2を要求するようになる。
