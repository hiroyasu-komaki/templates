> 📝 記入ガイド: **検証とエラー処理は、設計されないと必ず場当たりになる領域。** 実装者ごとにメッセージの文体も、ブロックするかどうかの判断もばらつく。ここで方針を統一する。
>
> 特に「どこまでブロックし、どこから警告に留めるか」は**プロダクトの性格を決める判断**。下書き文化を尊重するなら空欄でも進めさせる、厳密な業務なら必須を強制する、という選択がある。

## 2. 検証レベル

> 📝 記入ガイド: 何をどのレベルで扱うかを決める。**「エラー」を安易に増やさない。** 進行を止める理由が業務上あるものだけをエラーにする。

| レベル | 意味 | ユーザーの進行 | 表示 |
|---|---|---|---|
| エラー | 業務上あり得ない値 | ブロックする | |
| 警告 | 不備の可能性があるが進めてよい | 進める | |

## 5. エラーメッセージの方針

> 📝 記入ガイド: **文体を統一する。** 「〜してください」なのか「〜が必要です」なのか、体言止めか。決めておかないと画面ごとにばらつく。
>
> 良いメッセージは「何が」「なぜ」「どうすれば」が分かる。「エラーが発生しました」だけのメッセージを禁止する。

| 項目 | 方針 |
|---|---|
| 文体 | |
| 含める情報 | 何が問題か / なぜ問題か / どうすればよいか |
| 技術的な詳細の扱い | ユーザーには出さない。ログに記録し、参照IDのみ提示 |
| 禁止する表現 | 「エラーが発生しました」等の情報量ゼロのメッセージ |

## 7. API エラー応答の形式

```json
{
  "code": "{{機械可読なエラーコード}}",
  "message": "{{利用者向けメッセージ}}",
  "details": [
    { "field": "{{項目キー}}", "code": "{{}}", "message": "{{}}" }
  ],
  "traceId": "{{ログ追跡用ID}}"
}
```

| ステータス | 用途 | クライアントの扱い |
|---|---|---|
| 400 | 入力検証エラー | 該当項目にインライン表示 |
| 401 | 未認証 | ログインへ誘導 |
| 403 | 権限なし | |
| 404 | 対象なし | |
| 409 | 競合 | → §8 |
| 422 | 業務ルール違反 | |
| 500 | サーバエラー | 参照IDつきで再試行を案内 |

**未保存データの保護**
