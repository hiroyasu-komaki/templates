# 開発ドキュメント標準テンプレート（devdoc-template）

受託・社内開発プロジェクトの**開発者向けドキュメント一式**の標準構成。
一次資料（発注元資料・見積・プロトタイプ等）を受領してから、実装・テスト・リリースまでを一本の流れで記述できるようにしている。

---

## 0. 使い方（最初に読む）

### 0-0. まず、2つの使い方ガイドを読む

このテンプレートは**フルセットで使うことを前提としていない。** 案件に応じて章を取捨選択し、記載の深さを変えて使う。また、実装が先に存在するケースにも対応する。

| ガイド | 読むべき人 | 内容 |
|---|---|---|
| [使い方①: 案件に応じた取捨選択と記載粒度](./USAGE-01-tailoring.md) | **全員（着手時に必ず）** | 案件プロファイルの判定、章ごとの要否と粒度、規模を問わず必須の4章、省略の記録方法 |
| [使い方②: 実装済みシステムの後追い文書化](./USAGE-02-retrofit.md) | 実装が先に存在する場合 | 目的の決め方、出所タグ、逆順の執筆手順、陥りやすい罠、「正」への切り替え |

**着手時の判断**:

```
実装はまだ無い ──→ ①で章を選ぶ ──→ 本READMEの順序（00→08）で書く
実装が既にある ──→ ①で章を選ぶ ──→ ②の順序（資料→構造→意図→背景）で書く
```

### 0-1. 前提とする進め方

このテンプレートは **「一次資料 → 開発ドキュメント → 実装」** という順序を前提にしている。
開発ドキュメントは実装の**成果報告ではなく、実装の入力**である。したがって:

- **実装前に書ける内容だけで構成されている。** 「実装済み範囲」「現行コードとの差分」といった事後報告の章は持たない。
- 実装が始まった後の「実際にこうなった」は、[`06-roadmap/`](./06-roadmap/) のバックログと [`02-architecture/05-adr/`](./02-architecture/05-adr/) の意思決定記録に集約する。設計章は書き換える（履歴はGitに残す）。

> 実装が既に存在する状態から書き始める場合も、**成果物は同じ形になる**（現状の説明書ではなく、実装の入力となる設計）。そのための手順は [使い方②](./USAGE-02-retrofit.md) を参照。

```
[一次資料]                    [このドキュメント]                [成果物]
requirement/            →     devdocs/                    →    ソースコード
 ・発注元の要求資料             00 なぜ作るか                     実装・テスト
 ・設計アドバイス               01 何を作るか                     リリース
 ・見積書                      02-03 どう作るか
 ・プロトタイプ                 04-05 どう進め・どう検証するか
                              06-08 いつ・誰が・どう運用するか
```

### 0-2. コピーして始める手順

1. このフォルダをプロジェクトへ `devdocs/` としてコピーする。
2. [使い方①](./USAGE-01-tailoring.md) でプロファイルを判定し、**書く章と粒度を決めて記録する**。
3. `_templates/variables.md` を開き、プロジェクト固有の値を埋める。
4. 各ファイル内の `{{変数名}}` を置換し、`> 📝 記入ガイド:` のブロックを読んで本文を書く。
5. **書き終えたら記入ガイドのブロックは削除する。**（残っているファイル＝未完成、と判別できるようにするため）
6. 使わない章は削除せず、冒頭に `> ⛔ 本プロジェクトでは対象外。理由: ...` と明記して残す。**書かなかった理由が残ることに価値がある。**
7. 使い終わったら、`USAGE-01` / `USAGE-02` はプロジェクト側のコピーから削除してよい（テンプレートについての説明であり、プロジェクトの文書ではないため）。ただし ①§8 の判定記録は残す。

### 0-3. 記法の約束

| 記法 | 意味 |
|---|---|
| `{{PRODUCT_NAME}}` | 置換必須のプレースホルダ |
| `> 📝 記入ガイド:` | 何を書くかの指示。書いたら削除する |
| `> ⛔` | このプロジェクトでは対象外である旨の明示 |
| `（TBD: 〜）` | 未確定事項。確定期限と担当を併記する |
| `[任意]` | プロジェクト性質により省略可能な章 |
| `[資料]` `[実装]` `[推定]` `[未確認]` | 記述の出所。**後追い文書化のときに使う**（→ [使い方②](./USAGE-02-retrofit.md) §3） |

## 1. フォルダ構成と執筆順序

**上から順に書く。** 前の章が固まらないうちに次を書くと、後段の手戻りが大きい。

| # | フォルダ | 何を書くか | 主担当 | 書くタイミング |
|---|---|---|---|---|
| 00 | [00-overview](./00-overview/) | なぜ作るか。背景・課題・ビジョン・プラン比較・用語 | PO/BA・PM | 一次資料受領直後 |
| 01 | [01-requirements](./01-requirements/) | 何を作るか。業務ドメイン、UX方針、機能スコープ、非機能要件 | PO/BA・UX | 要件精緻化フェーズ（P0） |
| 02 | [02-architecture](./02-architecture/) | どう作るか（全体）。技術スタック、データモデル、API、拡張性、ADR | アーキ・テックリード | 設計フェーズ（P0） |
| 03 | [03-detail-design](./03-detail-design/) | どう作るか（詳細）。画面、入力部品、状態遷移、検証・エラー | UX・FE/BEリード | 設計フェーズ後半（P0終盤） |
| 04 | [04-implementation](./04-implementation/) | どう実装するか。実装方針、リポジトリ構成、開発環境、規約 | テックリード | 実装開始直前（P1冒頭） |
| 05 | [05-test](./05-test/) | どう検証するか。テスト戦略、受入基準、非機能検証 | QA | 設計と並行（P0〜P1） |
| 06 | [06-roadmap](./06-roadmap/) | いつ作るか。フェーズ計画、バックログ、将来拡張 | PM・テックリード | P0で初版、以降継続更新 |
| 07 | [07-project](./07-project/) | 誰が・いくらで作るか。WBS・工数、体制/SFIA、前提・除外・リスク | PM | 見積確定時 |
| 08 | [08-operations](./08-operations/) | どう届け・どう運用するか。移行、リリース、運用引継ぎ | DevOps・PM | 設計時に骨子、P3で確定 |
| — | [_templates](./_templates/) | 変数一覧、ADRテンプレ、議事録・課題管理のひな型 | — | 随時 |

### 章の依存関係

```
00 overview ──→ 01 requirements ──→ 02 architecture ──→ 03 detail-design ──→ 04 implementation
                      │                    │                    │
                      └────────────────────┴────────────────────┴──→ 05 test
                      │
                      └──→ 07 project（工数・体制） ──→ 06 roadmap（計画） ──→ 08 operations
```

## 3. 運用ルール

- **スコープ判断の正は [`01-requirements/03-functional-scope.md`](./01-requirements/03-functional-scope.md)。** 「その機能はやるのか」で迷ったらここを見る。ここと違う実装をしたくなったら、まずこのファイルを更新する。
- **設計を変えたら ADR を残す。** 「なぜその選択をしたか」は3ヶ月後に必ず失われる。[`02-architecture/05-adr/`](./02-architecture/05-adr/) に追記する。
- **一次資料は改変しない。** 一次資料は `requirement/`（別フォルダ）に原本のまま置き、本ドキュメントはその二次資料として位置づける。対応関係は [`00-overview/03-source-materials.md`](./00-overview/03-source-materials.md) に書く。
- **一次資料と本ドキュメントが食い違ったら**、スコープは `01-requirements/03-functional-scope.md`、設計判断は `02-architecture/05-adr/` を正とする。一次資料側の記述が古い場合はその旨を対応表に注記する。
- **各ファイルの冒頭に「出典」と「最終更新」を書く。** どの一次資料のどこに基づくかを追えるようにする。

## 4. 取捨選択と粒度

**全34ファイルを常に書く必要はない。** 案件プロファイル（S/M/L）ごとの要否・粒度は [使い方①](./USAGE-01-tailoring.md) を参照。

規模を問わず**必ず書く4つ**だけ、ここに再掲する。

| ファイル | 省略した場合に起きること |
|---|---|
| [機能スコープ](./01-requirements/03-functional-scope.md) | 「やる/やらない」の合意が口約束になる |
| [データモデル](./02-architecture/02-data-model.md) | 最も変更コストが高い箇所を、設計せずに作ることになる |
| [開発環境](./04-implementation/03-dev-environment.md) | 作った本人しか動かせない |
| [バックログ](./06-roadmap/02-backlog.md) | 「後で直す」が全て消え、簡易実装が本番に出る |

省略する章は削除せず、`> ⛔ 本プロジェクトでは対象外。理由: ... / 見直す条件: ...` を残す。
